# 限定カスタムVMに対するブラインド復元評価

**本番採用を見送った。** 2種類のseedで独立したJAR単体評価を行い、いずれも3メソッドの条件分岐、戻り値、状態への副作用が人間可読な疑似Javaに復元された。定常p50も3メソッドすべてで上昇した。

対象は、本リポジトリとは別の、著者個人が開発する非公開のPaperプラグインの一部メソッドであり、ここでは対象の具体的な識別情報(プラグイン名・クラス名・メソッド名・入力ハッシュ等)は意図的に記載しない。再現性に必要なのは手法と結果であり、対象アプリケーションの特定情報ではない。

## 対象と対照

同一の入力JARを、Paperの同じstrongレシピで比較した。対照はVMを無効にした。両群ともカプセルを使わず、試作は既存の明示選択型VMをベースにした。高頻度経路依存の除外が適用されるメソッドは選択から外した。変換レポートで選択・変換件数を確認した。

対象は、状態を変更する3つのメソッドとした:

| 対象 | 操作の形 | 検証した結果 |
|---|---|---|
| A | 件数ガード付きの状態切替操作 | 両方向の切替と、人数条件に応じた拒否判定 |
| B(開始) | 3つの事前条件に支配される二相操作の開始 | 条件の全8組。受理時の値生成、拒否時の既存状態保持 |
| C(終了、Bと対になる) | 2つの事前条件に支配される二相操作の終了 | 条件の全4組。受理時だけ状態を消去 |

試作は入力を独自命令に変換し、呼び出し時にはディスパッチャが命令語を直接評価する。初回はプログラムの整数配列を復号・キャッシュする。対象のJVM命令列やhidden classを実行時に組み立てる経路はない。JARに含む通常クラスはラッパー、ディスパッチャ、アプリAPIへのブリッジ等である。外部秘密・ネットワーク認証・ネイティブコード・解析ツール検出を用いていない。

## 形式の差

命令番号はグループ別に置換し、命令幅・ワード配置と基本ブロックの順序も生成時に決めた。主オペランドは仮想PC依存のXORと回転、副オペランドはPC依存の加算を使った。整数ローカルの状態は、マスクした1ワード、または上位・下位16ビットの別々の2ワードで表した。下表は実際に生成された組み合わせ。ログだけを追加した再生成で、各seedのJARの全5,086エントリの内容一致を確認した。

| seed | 対象グループ | 命令幅 | opcode / operand / extra の位置 | 主オペランド回転数 | 整数状態 | ディスパッチ |
|---|---|---:|---|---:|---|---|
| 20261122 | A | 3 | 1 / 2 / 0 | 6 | 2ワード | tableswitch |
| 20261122 | B/C | 6 | 2 / 3 / 1 | 24 | 2ワード | tableswitch |
| 99173 | A | 6 | 3 / 0 / 5 | 25 | 2ワード | lookupswitch |
| 99173 | B/C | 4 | 0 / 3 / 2 | 20 | 1ワード | tableswitch |

両seedで仮想スタック機械の計算モデルを共有する。2種類のswitchはどちらも同一の命令実装へ分岐する。

## 独立したJAR単体評価

評価役をseedごとに分け、対応するJARのみを渡した。対象名、mapping、元ソース、テスト条件、他方の評価結果は渡していない。固定カプセル解除器は両方ともカプセルサイト検出0件で終了した。

独立評価役はラッパーを発見し、文字列とプログラムワードの復号、命令幅・オペランド位置とPC依存変換の逆算、ディスパッチ先のスタック・ローカルへの作用からの命令同定を行った。さらにブリッジをフィールドやAPIへ対応付け、仮想PCの分岐・合流とスタック値を追跡した。いずれのseedでも、対象ごとの命令数は一桁〜三桁の範囲で読み取り、疑似Javaを生成した。追加の解析作業は必要になったが、状態更新と条件式はJAR内にそろっていた。

事前に定めた採点は、対象Aが7項目(切替方向の判定根拠、既定値、人数ガード、拒否、各方向の遷移、成功通知と返値)、対象Bが6項目(3前提、拒否時保持、生成値保存、成功返値)、対象Cが4項目(2前提、拒否時保持、消去と成功返値)。両者とも **17/17項目・3/3メソッド** を復元した。この値は入力フラグを含む実行条件と副作用の読解率である。元の変数名、命名意図、任意の別メソッドへの一般化や分析者の工数は採点していない。

## JVM、性能

Java 25、ローカル環境のメインスレッドで計測した。各条件1プロセス。対象ごとに初回を1回、1万回ウォームアップ後に2万回を測定した。初回にはMethodHandleの初回呼出し、クラス初期化、アプリ側の処理も含まれる。B/Cはランタイムを共有し、開始を終了より先に測った。対象Aの定常計測はテスト用の実行環境を使用し、分岐条件が変わる2状態を両seedで別ランで確認した。B/Cは実環境上で実メソッドを呼び出した。

| seed | 対象 | 初回 対照→VM (ms) | 対照 p50 / p95 / p99 (µs) | VM p50 / p95 / p99 (µs) |
|---|---|---:|---|---|
| 20261122 | A | 16.358 → 8.287 | 2.030 / 3.350 / 4.330 | 8.890 / 14.860 / 27.491 |
| 20261122 | B | 1.060 → 11.082 | 0.470 / 1.470 / 3.960 | 1.250 / 3.420 / 5.460 |
| 20261122 | C | 0.246 → 0.727 | 0.040 / 0.070 / 0.090 | 0.630 / 1.020 / 1.360 |
| 99173 | A | 5.091 → 8.394 | 1.901 / 3.130 / 3.800 | 10.241 / 12.081 / 24.431 |
| 99173 | B | 1.519 → 9.772 | 0.430 / 0.960 / 3.460 | 1.150 / 3.460 / 7.721 |
| 99173 | C | 0.305 → 0.563 | 0.110 / 0.140 / 0.170 | 0.580 / 0.950 / 1.310 |

対照・VM双方のJARサイズはVM版で数万バイト増加した(seedごとの正確な値は対象アプリケーションを特定し得るため割愛する)。

JDK 21のASMデータフロー検証と `java -Xverify:all` で、各seedのVM版・対照版ともに全クラスが通過した。各起動にも強制検証を指定した。

## 結論

Code Capsule v2の本番変更も別途取り消した(本リポジトリの `ce7b178`)。本番CLIを再ビルドし、standardのカプセル・VM回帰テストが成功した。限定VMの実装と生成JARはリリースに含めていない。

この結果が示すのは、**命令幅・オペランド位置・回転数・ディスパッチ種別をビルドごとに変えるだけの限定カスタムVMは、ブラインド評価者による手動リバースエンジニアリングに対して実用的な耐性を持たない**ということである。対象アプリケーションを特定し得る詳細を伏せても、手法と数値結果自体は再現・検証可能であり、将来同種のアプローチを検討する際の先行知見として残す。
